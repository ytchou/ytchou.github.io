# 實測 Caveman 的 Token 節省效果

## 前言


近期網路上流傳能大幅減少 Claude Code token 用量的 Skill: Caveman，號稱只要使用這個 Skill 平均就可以減少 76% 的輸出 token。原理是注入一段系統提示詞，叫 Claude「像聰明的原始人一樣簡短回覆」，砍冠詞、贅字、客套話和模稜兩可的回應，只留技術實質。

這個 Skill 真的有這麼神嗎？我們設計了四種情境，總共跑了近 600 次相同的流程來驗證 Caveman 的效果。結論是：Caveman 確實能減少 token 使用量，但在 Claude Code 中的效果遠不如宣稱。經過實測，透過 API 直接呼叫平均節省約 63%（與作者宣稱相去不遠），但到了 Claude Code CLI 卻只剩約 25%，僅為宣稱的 1/3。為什麼會有這個落差？答案在測試條件裡。


## Caveman 怎麼得到 76% 的結論？

在驗證之前我們需要先了解作者是怎麼得到他宣稱的結論。作者的流程很單純：準備 10 個程式設計任務的 prompt（涵蓋除錯、實作、重構、架構決策、程式碼審查、DevOps），分別在有 Caveman 和沒有 Caveman 的條件下各跑一輪，比較輸出 token 數的差異。

具體的測試條件：

- **模型**：`claude-sonnet-4-20250514`（2025 年 5 月的 Sonnet 快照）
- **基線系統提示**：「You are a helpful assistant.」——僅 6 個 token
- **Caveman 系統提示**：`SKILL.md` 的內容，指示模型「像聰明的原始人一樣簡短回覆」，砍冠詞、砍贅字（just/really/basically/actually/simply）、砍客套話、砍模稜兩可，只留技術實質
- **API 參數**：temperature=0（確定性輸出）、max_tokens=4,096、延伸思考關閉
- **每個任務跑 n=3 次**，取平均

在這組條件下，作者報告 10 個任務平均節省 75.8%，範圍從 22% 到 87%。

這裡有一個非常重要的前提：作者是直接呼叫 Anthropic API，並不是透過 Claude Code CLI，這表示作者得到的結論和我們實際在 Claude Code 的體驗可能會不相同，Claude Code 的 harness 可能會降低或是增強這個 Skill 的影響。

舉例來說，Temperature=0 會壓住輸出的隨機變異，傾向產生較短且一致的回覆。延伸思考關閉代表模型不會經歷可能擴展輸出的推理步驟。這兩點都跟 Claude Code 的預設數值並不相同（Claude Code temperature = 1.0，且延伸思考開啟）。此外，輸出上限 4,096 token 比 Claude Code 的預設值（16,384）少了四倍，而 6 token 的基線系統提示跟 Claude Code 實際的系統提示完全是兩個世界——後者塞了大約 18,000 token 的行為指令、程式設計理念、語氣規範和工具定義。

換句話說，作者的基準測試是在一個非常乾淨、非常可控的環境下跑的。這不是說測試有問題 —— 它確實測到了 Caveman 在那些條件下的效果。但 Caveman 是 Claude Code 的外掛，而這些條件沒有一個符合 Claude Code 的執行環境。

這就是我們想要回答的：把測試環境換成 Caveman 實際運行的地方，數字會變成什麼樣子？



## 方法論

### 實驗設計

四種情境各有各的任務：把「基準測試數字不能直接搬到實際使用」這件事拆成可獨立檢驗的因素。每種情境固定大部分變數，只動一個維度。

| 情境 | 測試框架 | 系統提示 | API 參數 | 任務數 | 每組條件執行次數 | 角色 |
|------|---------|---------|---------|-------|----------------|------|
| A | Anthropic API | 最小（6 token） | 作者設定：temp=0, max=4,096, 無延伸思考 | 10 | 10 | 重現作者的基準測試 |
| B | Anthropic API | 最小（6 token） | CC 匹配：延伸思考開啟（4K 預算）, max=16,384, temp=1.0 | 10 | 5 | 分離參數混淆因子 |
| C | CC CLI (`claude -p`) | 完整 CC 脈絡（~18K token） | CC 預設值（延伸思考開啟, temp=1.0） | 10 | 5 | 測量真實 CC 環境 |
| D | Anthropic API | 漸增式 CC 內容（6 層級） | CC 匹配 | 3 | 5 種排列 | 脈絡大小掃描以辨識崩潰機制 |

所有情境同一個模型（`claude-sonnet-4-6`）、同一組 10 個任務 prompt（取自作者上游基準測試）、同一份 Caveman 系統提示（`SKILL.md`）。每次執行都開全新對話，沒有脈絡延續。跟作者唯一的差異是模型版本（作者用 `claude-sonnet-4-20250514`，2025 年 5 月快照），以及我們把作者的 n=3 拉到 n=5 或 n=10 以取得更穩的中位數估計。情境 C 使用隔離設定目錄（`~/.claude-clean`）避免操作者個人設定汙染結果。各情境的完整細節見附錄。

### 情境 D：機制掃描

情境 A 到 C 確認了效果會衰減。但為什麼？兩個假說：

假設一：**Claude Code CLI 的 System Prompt 會稀釋掉 Caveman 的 Prompt**
Caveman 的 `SKILL.md` 約 1,000 token，隨著總脈絡從 6 token 膨脹到 18,000 token，影響力等比例被稀釋。跟內容無關，純粹是壓縮訊號被噪音蓋過。

假設二：**Claude Code CLI 的 System Prompt 有特定內容會干擾 Caveman 的 Prompt**
CC 系統提示裡有特定段落——語氣、風格、輸出效率指令——跟 Caveman 的壓縮指令正面衝突。模型收到矛盾指令，CC 那邊位置靠前、權限比較高的贏了。

情境 D 用來區分這兩個假說。我們把 CC 系統提示拆成兩塊結構上不同的東西：一個行為區塊（~3,500 token，含身份定義、程式設計理念、語氣/風格規範、輸出效率規則——跟 Caveman 最可能打架的內容）和 10 個工具定義區塊（每個 ~1,400 token，跟輸出長度無關）。然後逐步疊上去，在六個層級測量 Caveman 的效果：

| 層級 | 內容 | 約略系統 token 數 |
|------|------|------------------|
| L0 | 僅行為區塊 | ~3,500 |
| L1 | 行為 + 2 個工具定義區塊 | ~6,300 |
| L2 | 行為 + 4 個工具定義區塊 | ~9,100 |
| L3 | 行為 + 6 個工具定義區塊 | ~11,900 |
| L4 | 行為 + 8 個工具定義區塊 | ~14,700 |
| L5 | 行為 + 全部 10 個工具定義區塊 | ~17,500 |

情境 B（沒有 CC 內容，~6 token）和情境 C（完整 CC CLI，~18K token）是兩端錨點。我們挑了三個任務——按情境 A 節省幅度選，刻意涵蓋高中低：`error-boundary`（72%，高）、`async-refactor`（48.5%，中）、`pr-security-review`（32.7%，低）——在每個層級跑 5 種隨機工具定義區塊排列。共 180 次 API 呼叫。

隨機排列是為了確保每個中間層級裡，不同工具定義區塊出現在不同組合，讓區塊身份不會跟累積 token 數綁在一起。

### 指標

主要指標：輸出 token 節省——每個任務基線與 Caveman 條件之間中位數輸出 token 的百分比降幅。次要指標：每任務變異數（條件內標準差）和成本（按公開 Sonnet 4.6 定價算：$3/MTok 輸入、$15/MTok 輸出）。所有中位數按條件按任務算；跨任務的平均值是這些每任務中位數的平均值。

### 情境 A：宣稱可重現

用作者的方法跑，Caveman 確實壓得動。10 個任務全部往預期方向走。

![Token Savings by Task Across Tracks](charts/chart1-savings-across-tracks.png)

我們跑出 67.3%，比作者的 75.8% 低 8.5 個百分點。這跟模型版本漂移（Sonnet 4.6 vs 作者的 2025 年 5 月快照）和我們樣本量比較大（n=10 vs n=3，異常值的影響被壓下來了）是一致的。10 個任務方向全對。宣稱可重現。

有兩個任務比作者報告的省更多：`async-refactor` 和 `microservices-monolith`（各 +26 和 +30 百分點）。兩個都是文字重的任務；Sonnet 4.6 的基線輸出比 2025 年 5 月快照囉嗦，等於多給了 Caveman 可壓的素材。反過來，`postgres-pool`、`race-condition-debug`、`error-boundary` 三個低於作者 15-18 百分點。這幾個任務作者端的 Caveman 輸出異常低（n=3 時只有 159-456 token），小樣本的異常值效應是最合理的解釋。

### 情境 D：是干擾，不是稀釋

情境 D 抓到了兇手。衰減不是慢慢來的，是一刀就砍下去，而且可以指認到一個特定組件。

| 層級 | 脈絡 | async-refactor | error-boundary | pr-security-review |
|------|------|:--------------:|:--------------:|:------------------:|
| B（無 CC 內容） | ~6 token | 34.8% | 67.7% | 27.7% |
| L0（僅行為區塊） | ~3,500 token | 9.0% | 19.9% | 12.4% |
| L1 | ~6,300 token | 24.4% | 18.9% | 16.6% |
| L2 | ~9,100 token | 11.7% | 23.3% | 28.8% |
| L3 | ~11,900 token | 13.9% | 38.5% | 17.8% |
| L4 | ~14,700 token | 15.0% | 31.1% | 2.5% |
| L5 | ~17,500 token | 19.2% | 31.2% | 22.8% |
| C（CC CLI 實際） | ~18K token | +19.5% | +45.3% | -0.4% |

![Savings Collapse at the Behavioral Block](charts/chart3-interference-curve.png)

光是塞進行為區塊——約 3,500 token 的身份定義、程式設計理念、語氣/風格規範、輸出效率規則——效果就直接跳崖：

- `async-refactor`：34.8% → 9.0%（-25.8 百分點）
- `error-boundary`：67.7% → 19.9%（-47.8 百分點）
- `pr-security-review`：27.7% → 12.4%（-15.3 百分點）

從 L0 到 L5 繼續堆工具定義呢？沒有一致的進一步下降。L1 到 L5 的結果平坦又吵，看不出單調遞減。`error-boundary` 的節省甚至隨工具定義增加而*上升*。這跟稀釋假說完全對不上——稀釋預測的是脈絡越長效果越差，應該看到一路往下的曲線。

行為區塊裡面有什麼？CC 的「語氣與風格」和「輸出效率」段落，大約 600 token 在告訴模型要簡潔、別廢話、直奔重點、回覆要短。這跟 Caveman 的 `SKILL.md` 直接撞車——後者也在叫模型「簡短回覆」、「省略冠詞」、刪掉「贅字（just/really/basically/actually/simply）」。兩邊瞄準同一條壓縮軸。CC 有位置優先權：它在組裝好的 prompt 裡出現得比較早，是核心系統訊息；Caveman 是外掛注入、掛在後面。transformer 模型裡，指令衝突的時候，出現得早的系統提示通常有比較強的影響力。

拿 D-L5 跟情境 C 比，結果大致吻合：`async-refactor` 在 L5 是 19.2%，C 是 +19.5%（幾乎一樣）；`error-boundary` 是 31.2% 對 +45.3%（實際 CLI 裡反而更高）。`pr-security-review` 比較跑掉：L5 是 22.8%，C 是 -0.4%。三個任務平均起來差不多（L5 的 24.4% vs C 的 21.5%），代表 API 重建抓到了大部分測試框架效應。剩下的任務間差異可能來自 CLI 的動態脈絡（對話資訊、git 狀態、工作目錄）以及靜態 API 呼叫複製不了的多輪工具使用行為。

## 分析

### 落差分解

從情境 A 的 63.1% 掉到情境 C 的 +25.3%，總共衰減 37.8 百分點。拆開來：

| 來源 | 幅度 | 佔落差比例 |
|------|------|----------|
| API 參數（A 到 B） | -12.6pp | ~33% |
| CC 行為指令（B 到 D-L0） | ~30pp 平均 | ~48% |
| 工具定義與額外脈絡（D-L0 到 D-L5） | 可忽略 | ~0% |
| 剩餘測試框架效應（D-L5 到 C） | 不定，小量 | ~19% |

![What Causes the Gap Between Benchmark and Claude Code](charts/chart4-gap-decomposition.png)

參數有影響但不是主角。Temperature=0 壓住取樣變異性，傾向產生較短輸出；沒開延伸思考就少了一個可能擴展輸出的推理步驟。兩者都把表面節省灌大了。不過即使校正完參數，Caveman 在 B 仍有 50.6%，所以不能全怪參數。

主角是行為區塊。CC 的語氣、風格、輸出效率指令——3,500 token 行為區塊裡的大約 600 token——已經把 Caveman 想做的事做了大半。兩者同時存在的時候，模型不會乖乖壓兩次。它已經被叫要簡潔了，再來第二個「你給我簡潔」的指令，帶來的是增量壓縮，不是倍數壓縮。

D-L5 跟情境 B 之間的殘差平均約 3 百分點，因任務而異。CLI 測試框架在系統提示內容能解釋的範圍之外，沒有造成系統性的額外衰減。

### 干擾，不是稀釋

這個區別為什麼重要？如果是稀釋，那任何夠長的系統提示都會削弱任何外掛——你只能縮短脈絡，沒別的辦法。如果是干擾，那針對 CC 還沒管到的面向的外掛，不管脈絡多長，效果都不會被吃。

情境 D 的數據指向干擾。稀釋預測從 B 經 D-L0 到 D-L5 應有單調遞減，而且衰減跟內容無關。兩點都不成立。最大降幅出現在 D-L0（3,500 token 的行為指令）；之後每層級再加約 2,800 token 卻沒有造成一致的進一步下降。驅動崩潰的是內容，不是體積：3,500 token 的行為指令造成的降幅，比後面堆上去的 14,000 token 工具定義大得多。

說白了，對外掛開發者的啟示就是：你的外掛如果針對的是 CC 系統提示已經在管的輸出行為（長度、格式、語氣、結構），效果會被打折。但如果針對的是 CC 沒管的東西（特定領域的輸出格式、語言翻譯、超出 CC 預設的程式碼風格），就不會踩到這個干擾問題。這是可測試的假說，但不在本研究範圍內。

### 任務層級差異

情境 C 的跨任務差異很大。三個任務壓縮還是很猛：`auth-middleware-fix`（+57.5%）、`error-boundary`（+45.3%）、`react-rerender`（+43.4%）。兩個幾乎沒感覺：`postgres-pool`（+1.7%）、`pr-security-review`（-0.4%）。

這個模式跟 CC 壓縮各任務基線的力道大致對得上。CC 已經壓了 60-80% 的任務（`docker-multi-stage`、`postgres-pool`、`microservices-monolith`）根本沒剩什麼空間。CC 壓了 30-45% 的任務（`error-boundary`、`react-rerender`）還有肉，Caveman 也確實吃到了（+45.3% 和 +43.4%）。

但也沒有完美對應。`auth-middleware-fix` CC 基線已經壓了 54.8%，Caveman 照樣再砍 57.5%。`pr-security-review` CC 只壓了 33.9%，Caveman 卻幾乎掛零。任務本身的特性——涉及的文字類型、壓縮犧牲的是結構性內容還是可省的廢話、n=5 帶來的隨機震盪——引入了單純壓縮空間模型解釋不了的散佈。

### 成本影響

用作者的 API 參數跑，Caveman 的成本節省是紮實的：輸出從每任務中位數 1,537 降到 503 token，以 Sonnet 4.6 定價算每百萬輸出 token 省約 $15.50。但 Caveman 的 `SKILL.md` 每次呼叫多吃約 1,000 個輸入 token（$3/MTok 輸入），會部分抵消。淨節省存在，但比看原始百分比小。

到了 Claude Code CLI 就更淡了。+25.3% 的中位數節省，等於輸出平均少四分之一左右。情境 C 典型的 350-600 token 輸出，換算下來每次呼叫少 90-150 個輸出 token——以目前定價算就是零點幾美分的事。`SKILL.md` 的 1,000 token 輸入開銷甚至會吃掉一部分。如果你用的是 Claude Code 訂閱方案不是 API 計費，token 節省反映在回應速度上，不是直接省錢。

### 變異數

情境 C 多了一個 API 情境沒有的不穩定來源：多輪工具使用行為。偶爾會碰到某次執行觸發工具使用迴圈，輸出 token 數直接炸開。有一次 `pr-security-review` 衝到 6,853 token，正常才 400-600。n=5 的時候，一個這種異常值就能把平均值擺動好幾百個百分點，但中位數幾乎不受影響。這就是本研究情境 C 結果全用中位數報告的原因。作者的 n=3 對這類異常值更脆弱——我會說脆弱到不能忽視的程度。

## 啟示

### 基準測試必須符合部署條件

這次審計看到的模式不只適用於 Caveman。作者的基準測試不是故意灌水。它確實測到了 Caveman 在那些條件下的效果。問題是那些條件跟部署環境的偏離會一路疊加，而且方向一致——都往高估走。三個偏離因素：

1. **API 參數**：Temperature=0、無延伸思考、4,096 token 輸出上限，沒有一個是 CC 預設值。它們壓住了真實 CC 對話中的變異和輸出擴展，把表面壓縮灌大了約 12.6 百分點。

2. **系統提示內容**：6 token 的基線（「You are a helpful assistant」）製造了一個人為囉嗦的起始點。CC 的 18,000 token 系統提示自己就在叫模型產生簡潔輸出。拿沒壓縮的基線來測壓縮工具，測到的是理論上限，不是它在脈絡中的邊際貢獻。

3. **測試框架差異**：就算用 API 重建了 CC 的系統提示內容（情境 D），重建環境跟實際 CLI 之間還是有微小殘差。測試框架本身帶入了系統提示文字以外的效應，不過這些比前兩個因素小。

任何修改模型輸出行為的外掛都會撞上同樣的問題。用最小系統提示的原始 API 呼叫做基準測試，會系統性地高估跟部署環境自身指令競爭時的效果。解法不複雜：在部署環境裡測，別在簡化的替代環境裡測。

### 壓縮有上限，而且比宣稱的低

CC 的行為指令和 Caveman 的 `SKILL.md` 瞄準的是同一組輸出特性：囉嗦程度、贅字、模稜兩可、不必要的框架語言。兩者同時存在的時候，模型不會壓兩次。落點會在任一指令單獨效果和兩者在不同軸線運作能達到的效果之間。約 25% 的殘餘節省說明 Caveman 更激進的規則（省略冠詞、消滅贅字、原始人式極短）確實把輸出推到了 CC 的溫和簡潔指令之外。但邊際增益遠小於獨立效果。

我反覆觀察到的是：就這批程式設計任務而言，有用的技術輸出大概在 300-500 token 附近就到底了。再怎麼疊壓縮指令都壓不下去。這可能就是資訊密度的物理下限。

### 外掛驗證需要框架層級的測試

這段是對 Claude Code 外掛開發者說的。如果你的外掛會改輸出行為（長度、格式、語氣、結構），光靠原始 API 驗證不夠。你需要在 `claude -p` 或包含 CC 系統提示、工具定義和預設參數的等效框架中測。作者的基準測試框架作為 API 層級測量的起點可以用，但不夠撐住關於 Claude Code 實際效能的宣稱。

我們的落差分解替類似 Caveman 的外掛——針對輸出長度和語氣的——提供了一個粗略的修正係數：從最小 API 基準測試到完整 CC 環境，效果大小約有 60% 的相對縮水（63% 到 25%，約 60% 的相對降幅）。能不能推廣到針對其他輸出面向的外掛？不知道。API 基準測試拿來快速迭代 OK，但最終驗證必須在部署環境裡跑。

### Caveman 做到了什麼

講了這麼多缺點，要講公道話。Caveman 不是沒用。它的 `SKILL.md` 是一段寫得很好的壓縮指令。它在相對於最小基線的條件下砍掉 50-67% 的輸出 token，在 Claude Code 裡也保有約 25% 的節省。工程品質沒問題。問題是部署環境：Caveman 所在的地方已經把它想解決的問題解決了一半，留給它的空間自然就窄。

直接用 Anthropic API 搭配最小系統提示的使用者（聊天應用、簡單問答端點、沒有複雜系統指令的自訂整合），Caveman 的壓縮是貨真價實的。在 Claude Code 裡，效果溫和一些但確實存在：25% 的中位數輸出 token 減少，對在意回應速度的人來說是有感的改善。

## 結論

Caveman 有效。壓縮指令寫得好，隔離測試效果明確。問題不在外掛本身，在基準測試。用 6 token 的最小系統提示搭配人為的 API 參數去測量，上游基準測試抓到的是 Caveman 的天花板，不是它在部署環境中實際多幫了多少。

580 次執行、四種情境，本研究把基準測試（63%）與部署環境（25%）之間 38 百分點的落差拆成三塊：API 參數差異（~33%）、CC 行為指令的干擾（~48%）、剩餘測試框架效應（~19%）。機制是干擾，不是稀釋——CC 現有的簡潔指令搶先了 Caveman 的壓縮指令。脈絡的體積不是重點，重疊的內容才是。

65-76% 節省的頭條數字搬到部署環境就撐不住。Claude Code 裡的實測接近 25%。有改善，但跟宣稱的差距不小。外掛效能宣稱需要在工具實際運行的環境中量——這不是 Caveman 獨有的問題，是所有行為修改型外掛都該面對的。

## 附錄：情境 A/B/C 細節

### 情境 A：重現宣稱

情境 A 就是照抄作者的 `run.py`。直接用 Anthropic SDK，基線系統提示「You are a helpful assistant」，套作者的 API 參數（temperature=0、max_tokens=4096、無延伸思考），10 個任務全跑。跟作者唯一的差異是模型版本：我們用 `claude-sonnet-4-6`（當前 Sonnet），不是作者的 `claude-sonnet-4-20250514`（2025 年 5 月快照，2026 年 6 月 EOL），這樣才能跟其他情境對齊。

作者只跑了 n=3，我們拉到每個條件每個任務 n=10，共 200 次執行。多跑幾次，中位數估計穩一點，也比較容易抓到 n=3 會被蓋掉的變異。

### 情境 B：分離參數效應

情境 A 重現了作者的結果，但 API 參數跟 Claude Code 預設值不同。情境 A（63% 節省）跟情境 C（+25% 節省）之間的落差混了三個東西：系統提示內容、工具定義、API 參數。

情境 B 把參數的影響單獨抓出來。同一個 API 測試框架、同一組最小系統提示，但換成 Claude Code 的預設參數：temperature 不指定（預設 1.0）、max_tokens=16,384、延伸思考開啟且預算 4,000 token。100 次執行（10 個任務、2 個條件、每格 5 次）。

### 情境 C：真實環境測試

情境 C 不用 API 了，直接用 Claude Code CLI。透過 `claude -p --output-format json` 跑子程序。基線條件用 CC 完整的原生脈絡（~18,000 token 系統提示），透過 `enabledPlugins` 設定把 Caveman 關掉。Caveman 條件則用同一機制把外掛打開。

為了不讓操作者的個人設定汙染結果，所有情境 C 執行都用隔離設定目錄（`~/.claude-clean`），裡面沒有使用者的 `CLAUDE.md` 或自訂設定。兩個條件之間唯一的差異就是 Caveman 開不開。我們拿輸入 token 數來驗證啟用狀態：Caveman 執行比基線多約 1,000 個輸入 token（17,088 對 18,077），跟 `SKILL.md` 被前置注入的預期一致。100 次執行（10 個任務、2 個條件、每格 5 次）。
